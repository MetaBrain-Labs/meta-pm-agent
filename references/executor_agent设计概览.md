# Executor Agent 设计概览

## 一、核心设计理念

### 1.1 知识图谱即产品设计

产品知识图谱承载一款产品设计的所有内容及之间的关系，是产品设计的唯一真实来源（single source of truth）。Executor Agent 的全部产出均为知识图谱的节点和关系，而非独立的制品文档。PRD、战略文档、用户画像等传统交付物，应由 Document Agent 在需要时从图谱中组装生成。

### 1.2 设计原则

1. **图谱原生**：Executor 只产出图谱节点与关系，不产出任何独立文档。一切产品设计知识以图谱实体（目标/需求/依据/决策/功能/组件/指标）的形态存储。
2. **逐层细化**：每类 Executor 在其分工范围内，将上游节点逐层拆细（例如"功能" -> 子功能 -> 组件），通过 `构成` 关系建立层次。
3. **关系闭环**：新增实体必须嵌入现有的溯源链路：功能→决策→需求→目标，或功能→需求→目标，确保每个节点可追溯其"为什么存在"。
4. **技能映射**：每个 Executor Agent 的能力集合直接对应 pm-skills 目录下的 skill，底层仍调用 skill 的思维框架，但输出被系统定向为图谱操作。

### 1.3 统一接口

所有 Executor Agent 遵循相同的交互协议：

| 环节 | 内容 |
|------|------|
| **输入** | ProductDirector Agent 派发的任务描述 + 请求表单 + 已有产品上下文（含当前图谱） |
| **`<think>`** | 推理过程：理解任务目标、检索图谱现有相关节点、给出方案推导 |
| **`<execute>`** | 图谱更新指令（新增/修改节点、新增/删除/修改关系），每条指令须指定操作的实体类型、描述、附加说明、关联关系 |
| **`<error>`** | 错误信息（如有），含错误类型、关联节点 ID、描述、建议修正方式 |

### 1.4 图谱实体类型总览

Executor 的职责就是对以下实体进行增、改、关联。任何 Executor 均不越权创建实体类型范围外的输出格式。

| 实体类型 | 含义 | 示例 |
|---------|------|------|
| **目标** | 为什么做 | "提升复购率至 35%" |
| **需求** | 用户需要什么 | "需在下单 3 步内完成结账" |
| **依据** | 凭什么这么说 | "竞品分析报告 2025Q3"、"用户访谈记录 #42" |
| **决策** | 选择什么方案 | "接入 Stripe 而非自建支付" |
| **功能** | 构建什么能力 | "一键复购模块" |
| **组件** | 如何具体构建 | "Stripe Checkout API 封装"、"一键复购入口 UI 规范" |
| **指标** | 用什么评判 | "支付成功率"、"复购转化率" |
| **自定义** | 上述分类不覆盖的实体 | 由 agent 自行声明类型名 |

关系类型：**驱动 / 满足 / 影响 / 产生 / 限制 / 实现 / 衡量 / 验证 / 引用 / 构成 / 自定义**。

## 二、Executor Agent 清单

### 2.1 Product Strategy Executor（产品战略执行器）

| 属性 | 值 |
|------|-----|
| **ID** | `executor-product-strategy` |
| **图谱角色** | 创建和细化 **目标**、**决策** 实体，建立顶层因果链 |
| **能力来源** | `pm-skills/pm-product-strategy/` |

#### 技能 → 图谱操作映射

| Skill | 图谱操作 |
|-------|---------|
| `product-vision` | 创建顶层 `目标` 节点，并拆分为子目标（`构成` 关系） |
| `product-strategy` | 将战略分析结果拆解为多条 `决策` 节点，每个决策关联其驱动的 `目标` |
| `swot-analysis` / `porters-five-forces` / `pestle-analysis` | 创建 `依据` 节点（分析结论），通过 `引用` 或 `驱动` 关系关联到对应 `决策` |
| `value-proposition` | 创建 `需求` 节点（价值主张反应用户需求），通过 `驱动` 将需求关联到 `决策` |
| `ansoff-matrix` | 创建 `决策` 节点（增长路径选择），关联相关 `目标` |
| `business-model` / `lean-canvas` / `startup-canvas` | 创建/细化 `决策` 节点（商业模式选型），每个决策附依据引用 |
| `pricing-strategy` / `monetization-strategy` | 创建 `决策` 节点（定价/盈利模式），关联 `需求` 和 `目标` |

#### 图谱产出

| 主要创建 | 主要关系 | 说明 |
|---------|---------|------|
| 目标 | 构成（子目标→父目标） | 将业务目标逐层拆解为可衡量子目标 |
| 决策 | 产生（决策→功能）、驱动（需求→决策） | 每个决策明确标注其解决的需求和将产生的功能方向 |
| 依据 | 引用（依据→决策）、验证（依据→决策） | 战略分析作为决策的支撑证据 |
| 需求 | 驱动（需求→决策） | 高层级用户需求节点 |

#### 工作举例

- 接收 `business_model` 中的用户目标描述 → 创建图谱 `目标` 节点并拆分子目标
- 执行 SWOT 分析 → 将分析要点写入 `依据` 节点 → 通过 `引用` 指向相关 `决策`
- 制定定价策略 → 创建 `决策: 采用订阅制定价` → 关联 `需求: 中小团队需可预测月度支出` 和 `目标: MRR 月增 10%`

|-------|---------|

| 主要创建 | 主要关系 | 说明 |
|---------|---------|------|
| 依据 | 验证（依据→需求）、验证（依据→指标）、引用（依据→决策） | 每条研究发现独立成节点，形成可溯源证据链 |
| 需求 | 驱动（需求→决策）、构成（子需求→父需求） | 从研究中提炼的 JTBD 及用户约束 |
| 指标 | 衡量（指标→需求） | 研究过程中发现的量化标准 |

#### 工作举例

- 竞品分析 → 创建 5 个 `依据: 竞品发现` 节点 → 每个通过 `引用` 关联到对应的 `决策` 节点
- 用户画像构建 → 创建 3 个 `自定义: Persona` 节点（详细信息写在附加说明中） + 从每个画像提炼 3-5 个 `需求` 节点
- 市场细分 → 创建 `需求: 细分市场A的核心诉求`、`需求: 细分市场B的核心诉求` → `构成` 关系挂载到整体需求下

### 2.5 Product Execution Executor（产品执行执行器）

| 属性 | 值 |
|------|-----|
| **ID** | `executor-product-execution` |
| **图谱角色** | 将 **功能** 节点逐层拆细为子功能和 **组件**，建立实现层级的图谱结构 |
| **能力来源** | `pm-skills/pm-execution/` |

#### 技能 → 图谱操作映射

> 核心逻辑：所有传统文档任务（PRD、用户故事、Sprint 计划等）均被重新解释为图谱实体拆分和关联操作。真正的文档由 Document Agent 按需从图谱组装。

| Skill | 图谱操作 |
|-------|---------|
| `create-prd` | 拆细 `功能` 节点：将 PRD 中描述的每一个特性映射为子 `功能` 节点（`构成` 关系），将技术规格和约束映射为 `组件` 节点（`实现` 关系），将背景和目标关联到已有的 `依据` 和 `目标` 节点 |
| `user-stories` | 将用户故事逐条映射为 `需求` 节点（故事中的用户目标部分）和 `功能` 节点（故事中的解决方案部分），建立 `满足` 关系 |
| `job-stories` | 同上，按 Job Story 模板（情境→动机→期望结果）分别创建 `需求` 和 `功能` 节点 |
| `sprint-plan` | 更新 `功能` 节点的附加说明（写入所属 Sprint 编号、故事点估算），通过 `构成` 调整功能树的执行次序 |
| `brainstorm-okrs` | 创建/细化 `目标` 节点及其子目标（`构成`），为每个 Key Result 创建 `指标` 节点（`衡量` 关系） |
| `outcome-roadmap` | 创建 `决策` 节点（路线图决策），通过 `产生` 关联阶段性 `功能` 节点，按时间线在附加说明中标注 |
| `prioritization-frameworks` | 更新 `功能` 节点的附加说明（写入优先级框架评分），必要时通过 `构成` 重组功能树层级 |
| `test-scenarios` | 创建 `组件` 节点（测试场景描述），通过 `限制` 关联对应 `功能`（测试约束了功能的验收标准） |
| `stakeholder-map` | 创建 `自定义: Stakeholder` 节点（干系人信息），通过 `自定义` 关系（如"关注"）指向相关 `功能` |
| `strategy-red-team` | 创建 `依据` 节点（红队发现的风险与漏洞），通过 `验证` 关联被挑战的 `决策` |
| `pre-mortem` | 创建 `依据` 节点（事前验尸发现），通过 `限制` 关联 `功能`（风险信息约束功能设计） |
| `dummy-dataset` | 创建 `组件` 节点（模拟数据集描述），通过 `实现` 关联对应 `功能` 作为测试支撑 |
| `retro` / `release-notes` / `summarize-meeting` | 创建 `依据` 节点（回顾/发布/会议结论），通过 `引用` 或 `验证` 关联涉及的功能/决策 |

#### 图谱产出

| 主要创建 | 主要关系 | 说明 |
|---------|---------|------|
| 功能 | 构成（子功能→父功能）、满足（功能→需求）、影响（功能→目标） | **核心职责**：将上层功能拆细为可实现的粒度 |
| 组件 | 实现（组件→功能）、限制（组件→功能） | 每个功能对应的技术/规范落地要素 |
| 需求 | 驱动（需求→决策） | 从用户故事中提炼的细分需求 |
| 指标 | 衡量（指标→目标） | OKR 中的 KR 指标 |
| 依据 | 验证（依据→决策）、限制（依据→功能） | 风险分析、会议纪要等 |

#### 工作举例

- 功能拆分：收到 `功能: 支付模块` → 创建子节点 `功能: 信用卡支付`、`功能: 电子钱包支付`、`功能: 支付结果通知` → `构成` 关系挂载 → 为每个子功能创建 `组件: Stripe API 封装` → `实现` 关系
- 用户故事处理：`故事: 作为用户，我希望一键重购上月商品` → 创建 `需求: 减少重复选购时间` → 创建 `功能: 一键复购` → `满足` 关系 → 在 `功能` 附加说明中写入验收标准
- Sprint 规划：读取优先级最高的 `功能` 节点树 → 在附加说明中标注 `sprint: 1`、`story_points: 5` → 确认 `功能` 之间若有依赖则通过附加说明标注 `depends_on: [node_id]`
- 功能→组件细化：`功能: 订单全文搜索` → 创建 `组件: ElasticSearch 索引结构定义`（`实现` 关系）、`组件: 搜索结果 UI 交互规范`（`实现` 关系）、`组件: 搜索响应时间 <200ms 性能约束`（`限制` 关系）

## 三、图谱驱动的任务执行流程

### 3.1 一次完整的图谱更新周期

```
用户输入
  │
  ▼
Conversation Agent ─── 拆解用户输入
  │
  ▼
Request Agent ─── 归类为 business_model
  │
  ▼
ProductDirector Agent ─── 读取图谱当前状态 → 决策需要哪些图谱操作
  │
  ├─→ Planner Agent ─── 规划图谱操作 DAG（以图谱实体类型为任务粒度）
  │
  ▼
ProductDirector Agent ─── 按 DAG 次序派发图谱操作任务
  │
  ├─→ Market Research Executor ─── <execute>: 创建 依据 + 需求 节点
  ├─→ Product Strategy Executor ─── <execute>: 创建 目标 + 决策 节点, 关联上游需求
  ├─→ Product Discovery Executor ─── <execute>: 创建 功能 节点, 满足 需求
  ├─→ Product Execution Executor ─── <execute>: 拆细功能, 创建 组件 节点
  ├─→ AI Shipping Executor ─── <execute>: 补全 组件 技术约束
  ├─→ Marketing Growth Executor ─── <execute>: 创建 指标 节点, 衡量 目标
  ├─→ Interface Craft Executor ─── <execute>: UI 质量审视 + 反模式检测
  │
  ▼
Critique Agent ─── 检查图谱更新质量（元模型合规、溯源链完整、无孤立节点）
  │
  ▼
Document Agent ─── 从图谱按需组装文档（PRD / 战略文档 / 用户画像报告……）
  │
  ▼
用户确认 ─── 合并图谱更新 或 回滚
```

### 3.2 以图谱实体为中心的任务粒度

Planner Agent 规划 DAG 时，任务粒度为图谱实体类型的操作，例如：

- "创建 `依据` 节点：竞品 X 的定价分析"
- "将 `功能: 支付模块` 拆分为 3 个子功能"
- "建立 `衡量` 关系：`指标: 支付成功率` → `需求: 快速结账`"

ProductDirector Agent 根据任务涉及的实体类型，映射到能处理该类型的 Executor Agent。

### 3.3 "构成"关系驱动的层层细化

产品设计逐层细化的核心机制是 `构成` 关系：

```
目标: 提升 GMV 20%（顶层）
  └─ 构成 → 目标: 提升复购率至 35%
               └─ 驱动 → 需求: 一键复购历史订单
                            └─ 驱动 → 决策: 构建复购快捷入口
                                         └─ 产生 → 功能: 一键复购模块（顶层功能）
                                                      └─ 构成 → 功能: 历史订单推荐算法
                                                      │           └─ 实现 → 组件: 协同过滤推荐引擎
                                                      └─ 构成 → 功能: 复购确认 UI
                                                                  └─ 实现 → 组件: 复购入口 UI 规范
                                                                  └─ 限制 → 组件: 复购流程 ≤ 2 步
```

每个 Executor 在其分工的层级上操作：
- **Strategy Executor** 创建目标和顶层决策
- **Research Executor** 创建依据和需求
- **Discovery Executor** 将需求映射到功能
- **Execution Executor** 将功能拆细为子功能和组件
- **Shipping Executor** 补充技术组件和约束
- **Interface Craft Executor** 对 UI 组件进行质量审视和反模式检测（侧翼，不参与主溯源链）
- **Toolkit Executor** 处理合规和辅助任务（大部分产出不参与主链路）

### 3.5 Executor 独立性

每个 Executor 的系统提示词**只描述自身职责**，不引用、不比较、不依赖任何其他 Executor。通过自动化测试脚本 `tests/test_executor_isolation.ps1` 验证全部 20 个中英文系统提示词的隔离性。原则如下：

- **自描述**：每个 Executor 只声明自己创建哪些实体、使用哪些关系
- **不提及同行**：不出现其他 Executor 的名称，不包含"唯一/第一个/最/其他 Executor"等比较性声明
- **不分配职责**：不写"X 由某 Executor 负责"，而是写"X 在你的工作流程中不创建"
- **仅知 ProductDirector**：只知道 ProductDirector Agent 派发任务、Document Agent 组装文档——这两个是框架级契约，不是同行 Executor

### 3.6 Executor 间协作边界

- **上游产出**：Executor 在 `<execute>` 中写入图谱节点和关系。
- **下游消费**：后续 Executor 在 `<think>` 阶段读取图谱的当前状态，基于已有节点执行本阶段操作。
- **冲突处理**：若 Executor 发现其产出与已有节点冲突，在 `<error>` 中注明冲突节点 ID 和建议，由 ProductDirector Agent 裁决。
- **节点 ID 稳定性**：节点创建即分配唯一 ID，后续 Executor 通过 ID 精确引用上游产出，避免描述歧义。

## 四、设计依据

### 4.1 图谱优先 vs 文档优先

传统 PM 工具链以文档为中心（PRD、策略文档、用户画像报告……），文档之间靠人工维护一致性。本系统的核心设计选择是：

| | 文档优先 | 图谱优先（本系统） |
|---|---------|------------------|
| 存储形式 | 多份独立文档 | 统一知识图谱 |
| 关系维护 | 手动交叉引用 | 关系边天然连接 |
| 溯源能力 | 难以保证 | `功能→决策→需求→目标` 链路天然可查 |
| 一致性 | 靠流程保证 | 单一数据源，无冗余冲突 |
| 文档产出 | 各角色各自编写 | Document Agent 从图谱按需组装 |
| 变更影响分析 | 人工排查 | 沿关系边遍历即可 |

### 4.2 按 pm-skills 子目录映射 Executor

每个 Executor Agent 的技能集合对应用一个 pm-skills 子目录。这不是随意的分组，而是因为：

1. **技能内聚**：同一子目录内的 skills 操作相同层级的图谱实体，共享相同的思维框架。
2. **角色对齐**：产品经理的角色分工（战略→研究→上市→探索→执行→增长→分析→交付）自然对应图谱中不同实体类型的创建和细化角色。
3. **独立演进**：每个 plugin 可独立迭代，新增 skill 只会扩展对应 Executor 的能力，不影响其他 Executor。

### 4.3 文档是图谱的视图

Document Agent 的职责是：收到 ProductDirector Agent 的请求 → 遍历图谱中指定范围的节点和关系 → 按目标文档模板渲染输出。例如：

- **组装 PRD**：遍历指定 `功能` 节点的子树（`构成` 关系），收集关联的 `需求`、`决策`、`依据`、`组件`，按 PRD 模板填入各节。
- **组装用户画像报告**：遍历 `自定义: Persona` 节点及其关联的 `需求`、`依据` 节点。
- **组装战略文档**：遍历 `目标` → `决策` → `依据` 的因果关系链。

Executor Agent 不感知这些视图的存在，专心于产出高质量、高内聚的图谱内容。

### 4.4 元模型对齐

| 实体类型 | 主要创建 Executor | 主要细化 Executor |
|---------|------------------|------------------|
| 目标 | Product Strategy | Product Execution（OKR 拆分） |
| 需求 | Market Research、Product Strategy | Product Discovery、Product Execution |
| 依据 | Market Research | Product Discovery、Data Analytics、AI Shipping、Interface Craft（审计/反模式） |
| 决策 | Product Strategy、Go-to-Market | Marketing Growth |
| 功能 | Product Discovery | Product Execution（拆细） |
| 组件 | Product Execution、Go-to-Market | AI Shipping（技术约束）、Interface Craft（UI 规范）、Toolkit（隐私合规） |
| 指标 | Marketing Growth、Product Discovery | Data Analytics |
| 自定义 | Toolkit | — |

### 4.5 系统提示词优化设计

基于对 Anthropic Claude Fable 5 / OpenAI GPT-5 Codex / Google Gemini 3.5 / Cursor 等主流系统提示词的深入研究（详见 `research/` 目录），所有 Executor 系统提示词应用了以下优化：

| 优化项 | 说明 |
|--------|------|
| **FORBIDDEN 禁止输出** | 每 Executor 明确列出 `<execute>` 块中禁止出现的 5 类内容（自由文本、模糊措辞、跨 Agent 引用等） |
| **BAD EXAMPLE 错误对照** | 每 Executor 含 2 组 bad-example（自由文本输出 + 模糊描述），标注 WHY BAD |
| **NEVER/ONLY 锚点词** | 关系使用指南和边界章节使用大写命令词提升约束遵循度 |
| **技能描述表格化** | 技能章节从长篇描述压缩为表格 + 引用 SKILL.md，消除信息重复 |
| **描述性语言压缩** | 去除"你不是在写xxx文档"等重复性描述，节省 20-25% token |

系统提示词更新由 `tests/test_executor_isolation.ps1` 自动化回归验证。
