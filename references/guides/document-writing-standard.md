# 文档编写标准规范(document-writing-standard)
撰写任意文档前，应恪守以下标准规范：

## 命名规范
产品文档标题的命名必须可以准确表达文档的定位和类型并且不准引起歧义。

通用的命名规则为：描述对象+版本号，例如产品需求文档 V1.0。

版本号具体规划查看[版本规范](#版本规范)章节。

## 格式规范
除非特殊要求，否则文档格式应使用 Markdown 文本类型，并遵守以下正文规范：

### 标题层级规范
文档只使用一个一级标题 `#`，作为文档名称，与文档的系统文件名称保持相同。

正文层级从二级标题开始，禁止跳级使用标题，例如 不要从 `##` 直接跳到 `####`。

减少层级数量，尽量仅分到3级，即`###`；除非特殊情况，否则不要写到4级及以上。

### 文档基础信息
文档开头，一级标题下应使用 Markdown 表格填写修订记录，便于追踪文档元数据及变动历史。

至少包含：

+ 文档版本
+ 创建日期(格式为YYYY-MM-DD)
+ 版本简述/修订简述

### 文档目录
长文档应在文档基础信息模块后添加文档目录，例如：

```markdown
## 目录

- [背景](#背景)
- [产品目标](#产品目标)
- [功能范围](#功能范围)
- [页面与交互](#页面与交互)
- [验收标准](#验收标准)
```

###  段落与列表规范
段落之间用空行分隔，不要连续堆叠大段文字。如果一个段落超出4句话，应考虑重新组织段落。

使用列表描述并列内容；使用有序列表描述有明确顺序的内容。

### 表格规范
 使用表格描述文档基础信息、字段、状态、规则、权限、配置项等结构化信息。例如：

```markdown
| 字段名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| phone | string | 是 | 用户手机号 |
| code | string | 是 | 短信验证码 |
| loginType | enum | 是 | 登录方式 |
```

要求：

+ 表头命名清晰。 
+  同类表格字段顺序保持一致。 
+  不要在单元格中写过长段落。 
+  复杂逻辑不要强行塞进表格，应拆成说明段落。

###  代码、字段和接口格式
使用行内代码格式描述程序代码、字段名、状态值、接口路径、枚举值应使用。例如：

```markdown
接口地址为 `/api/login/send-code`。

登录状态包括 `logged_in`、`logged_out`、`expired`。
```

### 流程图与状态图
简单流程可以用文字列表描述；复杂流程、思维导图使用 Mermaid 表述。

涉及业务泳道图使用 plantUML 表述。

## 版本规范
版本号是用来识别当前版本的方式。

采用“VX.Y”的格式：V代表版本号，X为主版本，Y为次版本号，X、Y都为非负的整数。

初次创建文档后，版本固定为V1.0。

文档版本更新的通用规则：

+ 当对文档进行大规模修订时，修改、叠加第 1 位数字。即X+1，Y归0。例如：V1.1变更为V2.0。
+ 当对文档进行中小规模修订时，修改、叠加第 2 位数字。即Y+1。例如：V1.0变更为V1.1。

## 表达规范
文档撰写过程中，注意文本表达的规范，尽量避免使用口语化的表达，例如“我认为”、“我觉得”、“俺寻思”、“接下来我们”、“那咱们”等表达句式。口语化的表达会降低文档的专业性和严谨性，同时给读者留下不专业的印象。

## 内容规范
禁止将对话内容编写进文档中。每份文档都必须作为最终产物，而不是中间的临时产物。
